# B站切片（Android）

一个 **41KB** 的安卓 App：B站链接 → 下载最低画质 → 按需压缩 → 自动切成每段 ≤10MB →
存进片库 → 一键发微信。

不用 Gradle、不含 AndroidX、**不打包 ffmpeg**（靠系统自带的 MediaCodec / MediaMuxer 干活）。

## v6.3 缩放再提速一倍：映射表 + 平面特判

原计划做「解/编流水线并行」，先量了一下数据：

```
yuv transcode done drop=0 idle=11 loops=512
```

- `drop=0`：编码器没有吃不下而丢帧的情况，说明不存在输入缓冲饥饿
- `idle=11/512`：循环里只有 2% 的轮次什么都没干

结论：**硬件解码和编码本来就在硬件里并行跑，串行循环没有明显浪费**，
上多线程收益有限、风险不小，所以改从真正的大头下手 —— 缩放函数本身。

### 改了两处

1. **横向映射表只算一次**
   以前每行每像素都做一次 `(long) x * w / dw`：
   500 帧 × 3 个平面 × 848 像素 ≈ **127 万次除法**
2. **按平面特判**
   - `Y` 平面（pixelStride 1）：直接 `dstBuf[x] = rowBuf[xmap[x]]`，不走 `System.arraycopy`
   - `UV` 交错平面（stride 2）：一次搬两个字节

### 实测（1920x1200 → 848x528，20 秒，压到 855k）

| 版本 | 耗时 | 折合 |
|---|---|---|
| v6.1（逐像素 ByteBuffer） | 4.49s | 4.5× 实时 |
| v6.3（映射表 + 特判） | **2.29s** | **8.7× 实时** |

同时加了 `KEY_OPERATING_RATE`（告诉编码器按目标帧率实时跑），但它只带来约 2% 提升，
说明这台机器的编码器本来就跑得挺满。

## v6.2 跳过片头的那段不再转码

「跳过开头 N 秒」= **把片头删掉不要**，成品从第 N 秒开始（这点一直是对的）。

但原来的做法是：整条视频（含片头）全部解码+编码一遍，切分时再把片头切掉 ——
片头白白算了一遍。

现在要压缩时先做一次**样本级预裁剪**（不解码，只搬数据，几百毫秒），
再拿裁好的文件去压缩：

```java
Splitter.extractRange(raw, cut, startUs, cutEnd);   // 纯拷贝
Transcoder.transcode(cut, enc, ...);                // 只压有效区间
```

实测（1920x1200 / 20 秒，跳过开头 10 秒，压到 855k）：

| | 转码耗时 | 输出 |
|---|---|---|
| 旧：转完再切 | 4.46s | 1.07MB / 10s |
| 新：先裁再压 | **2.43s** | 1.07MB / 10s |

快了 45%，成品完全一致。片头越长省得越多（跳过 28 秒那种收益更明显）。

不需要压缩的时候本来就是纯拷贝裁切，比这还省，不受影响。

## v6.0 处理中也能接新链接（排队）+ 多P 体验 + 缩放大提速

### 1. 回归修复：处理中复制的新链接被丢掉

```java
// 有任务在跑、或用户刚手动操作过，就先别插队
if (Jobs.isRunning()) return;      // ← 这一行把新链接直接扔了
```

早期是排队的，后来加这行「别插队」就变成了**静默丢弃**。现在：

- 主界面自动识别：忙也照收，`Jobs.enqueue` 自己会排到队尾
- 悬浮球：忙的时候不弹面板，直接入队并提示「已排队，前面处理完接着做」
- 保护窗口从 5 秒缩到 1.2 秒（只防「刚点完按钮焦点被抢」）

### 2. 多P 选集页

| 改动 | 说明 |
|---|---|
| 底部显示预估体积 | `已选 3 / 12 · 约 45 MB`（按时长 × 码率估算） |
| 一次勾 ≥8 个要确认 | 弹窗显示总量，防止手滑把整部番剧排进去 |
| 提交后不关页面 | 选中清空、提示「可继续选其他 P」，不用重新走一遍链接 |

### 3. 意外发现：降分辨率反而更慢

实测同一段 37 秒视频：

```
不缩放（848→848）：2.9 秒
降分辨率（848→640）：8.3 秒      ← 慢 2.6 倍
```

原因是缩放用的是 **ByteBuffer 绝对下标逐像素 get/put**：

```java
db.put(di, sb.get(si));   // 每像素两次带边界检查的绝对读写
```

800 帧就是几千万次。改成「整行取到 byte[] → 数组里挑点 → 整行写回」：

```
1920x1200 → 848x528，20 秒视频：4.49 秒
```

### 实测汇总（红米 12T）

| 场景 | 耗时 |
|---|---|
| 848x576 → 848x576，37s（纯拷贝） | 2.9s |
| 1920x1200 → 848x528，20s（缩放+编码） | 4.5s |

## v5.7 加速：硬件编码器 + 去掉三处无谓开销

用户要求「除了下载以外的流程提速」。找到四个瓶颈：

### 1. 一直在用软件编码器（最大头）

```java
// 之前
String[] names = {null, null, "c2.android.avc.encoder", "OMX.google.h264.encoder"};
```

`createEncoderByType` 在小米上经常给到 `c2.android.avc.encoder`（纯软编），
后两个兜底也全是软件编码器 —— 等于从没用过硬件。

现在用 `MediaCodecList` 枚举 + `isHardwareAccelerated()`（API 29+）显式挑硬编：

```
yuv encoder=c2.qti.avc.encoder      ← 高通硬编
```

### 2. 转码路径会记忆

`encPath2` 记住这台机器哪条路能通：先试 Surface 直通（解码器直接写编码器表面），
失败才落 YUV，并把结果存下来，下次不再重复试。

实测这台机器 Surface 两次都抛 `IllegalStateException`（硬件/默认都不通），
探测只花 ~100ms 就回落 YUV，代价可忽略。

### 3. 删掉整文件扫描

`Splitter` 原来为了「按字节找切点」遍历全部样本（`cumBySecond`），
切点改成按时间均分后这笔开销完全多余 —— 直接用文件长度。

### 4. 时长与入库

- `durationOf` 先读 `MediaExtractor` 轨道里的 duration，读不到才退回 `MediaMetadataRetriever`
- `Store.saveToDownloads` 用 `FileChannel.transferTo` 通道传输，不再 64KB 循环搬

### 5. 顺带修：目标大小压完还是被切成两段

CBR 实际输出比理论高 10~15%（关键帧开销），按原公式压完 2.10MB > 2MB 目标，
又被 Splitter 拆成两段。预算系数改到 0.85：

```
输入 4.53MB / 37s → 整片目标 2MB
输出 1.97MB，1 个文件 ✓
```

### 实测（红米 12T）

| 步骤 | 之前 | 现在 |
|---|---|---|
| 37s 视频转码 640x432 | ~14s（软编折算） | **8.3s**（硬编） |
| 切分 | 先扫全文件样本 | 直接按文件长度 |
| 入库 | 64KB 循环 | transferTo |

## v5.5 整片目标大小 + 裁头裁尾 + 只看未发

### 1. 整片目标大小（按「一个文件多少 M」来压）

设置里新增「整片目标大小（MB）」：填 12，就整条压成 **一个文件、≤12MB**，不再分段。

```
总码率 = 目标字节 × 8 ÷ 有效秒数
视频码率 = 总码率 − 音频 64k
分辨率按码率自适应：>700k→848 宽，>420k→720，>260k→640，其余 480
```

关键细节：**先判断原片够不够小**。裁切后的内容本来就 ≤ 目标时，只裁剪、不重编码
（省时间且画质无损）：

```java
double effBytes = srcKbps * 1000.0 * seconds / 8.0;
boolean needCompress4Total = byTotal && effBytes > totalMb * 1e6 * 0.95;
```

填 0 或不填 = 回到原来的「每段上限」规则。

### 2. 跳过开头 / 裁掉结尾（秒）

`Splitter.split()` 增加 `startUs / endUs`：

- 段数按**有效时长**算（总长 − 跳过 − 去尾）
- 首段从 `startUs` 开始，末段在 `endUs` 结束，切点仍吸附关键帧
- 不需要压缩时也走 Splitter（只搬样本，画质无损）
- 超过总长会直接报错，不会切出空文件

### 3. 只看未发 + 标已发

- 片库头部「只看未发」开关（状态记在 prefs）
- 多选条新增「标已发」：选中的片段一次标记，配合上面的筛选清账

### 实测（手机）

设置：整片 ≤5MB、跳过开头 10 秒 → 处理一个 37.0 秒 / 4.53MB 的本地片段：

```
输出：27.013 秒（37 − 10 ✓）、3.32MB（≤5MB ✓）
原片本来就够小 → 只裁剪，没有重编码
```

之后把设置调成「整条 ≤12MB、不跳过」作为默认。

## v5.1 本地视频 + 平板适配

### 新增：不用链接，直接选手机里的视频

首页多了「选本地视频」（`ACTION_OPEN_DOCUMENT` + 多选），选中的文件走和链接完全一样的

### 平板（小米平板5）上踩的三个坑

| 现象 | 原因 | 修法 |
|---|---|---|
| 片库永远「还没有片子」 | 片库里加了 `DURATION` 列，平板的 downloads 集合不认识这个列，查询直接抛异常被吞 | 查询失败自动退回不带时长的列 |
| 状态卡在「处理中」但什么都没跑 | 工作线程入口 `WorkService.start()` 在平板上抛异常，线程死了，但队列仍认为在忙 | 启动前台服务加 try/catch；`pending()` 只算活着的线程 |
| `每段 ≤9.000000381469727 MB` | prefs 存 float，读出来转 double 带尾巴 | `trimNum()` 先四舍五入到 1 位 |

安卓 11+ 的作用域存储：应用默认只能看到**自己写入**的文件。adb 拷进去的文件在系统媒体库里，
但片库查不到。要让片库也能列出外部拷入的文件，得申请「所有文件访问」并把列表改成文件遍历 ——

## v5.0 全流程测试：找到 4 个真 bug

用户报「弹窗卡片开着时只有第一个链接能用，后面复制新链接还是识别旧的」。顺着这条线索实测，
挖出四个互相叠加的问题：

### 1. 旧面板的定时器会关掉新面板（最隐蔽）

```
03:49:08 panel shown   ← 「正在解析…」面板，注册 15s 自动关闭
03:49:14 panel shown   ← 解析完 → 选项面板，注册 40s 自动关闭
03:49:23 ???          ← 15s 那个定时器到点，dismissPanel() 把「选项面板」关掉了
```

`dismissPanel()` 关的是**当前的** panel，不管它属于哪一代。所以选项面板常常刚出来就消失，
表现就是「点了没反应 / 又回到旧内容」。修法：加 `panelGen` 代次计数，定时器只在
`gen == panelGen` 时关闭。

### 2. 抢焦点读剪贴板会打断「复制」本身

点「复制」的瞬间系统还没写完剪贴板，这时立刻插一个可聚焦窗口，可能把这次复制打断，
于是永远读到上一次的内容 —— **这正是「一直识别旧链接」的直接原因**。
改成点击后延迟 450ms 再读。

### 3. 自动识别会吃掉自己复制的链接

从记录页长按「复制链接」再回主界面，「自动识别」立刻把这条又下一遍（还会弹「已经处理过」）。
改成复制时记 `selfCopiedUrl`，自动识别和悬浮球轮询都会跳过这一条。

### 4. 去重逻辑其实是坏的

原来 `sig = url + "#" + System.currentTimeMillis()` —— 时间戳每次都变，判断永远不成立。
改成用**剪贴板自身的 timestamp**，同一条链接重新复制也能再次触发。

### 实测（真机）

```
focus try=0 focus=true url=https://v.douyin.com/q8mgWzfGasw/   → 面板「牛魔战士…」
（复制另一条记录后）
focus try=0 focus=true url=https://v.douyin.com/LVH17lowm3o/   → 面板「肌肉小绿鸟…」
```

新链接识别正确，面板也不再莫名消失。

### 顺带加的

- 面板加「重新读」按钮：读错了可以当场重读，不用退出重来
- 记录页长按可「复制链接」

## v4.4 「每段时长」不再无视体积上限

**问题**：设置成「每段 9MB / 每段 4 分钟」后，会切出 28MB + 2MB。
**原因**：`Splitter.split()` 里只要 `partUs > 0`（填了每段时长）就**完全忽略体积**：

```java
if (partUs > 0) {
    n = ceil(durUs / partUs);      // 只看时长
} else {
    n = ceil(total / partBytes);   // 只看体积
}
```

4 分半钟的视频按 4 分钟一刀切 → 第一段 4 分钟（28MB，早就超了 9MB），第二段 30 秒（2MB）。

**改成两个限制同时生效，谁先到按谁切**：

```java
int nBytes = ceil(total / partBytes);          // 按体积要切几段
int nTime  = ceil(durUs / partUs);             // 按时长要切几段
int n = max(nBytes, nTime);                    // 取大的
```

切点仍按时间均分 + 吸附关键帧，所以每段既不超过体积上限，也不超过设定时长。

**顺带修**：压缩目标码率原来按「每段时长」算，视频短、体积是主要限制时会压得过狠
（比如 1 分钟一段的视频算成 300k）。改成取「每段时长」和「按体积算出的段长」里更小的那个。

**实测**（30.2MB / 130 秒抖音视频，设置 9MB / 4 分钟 / 900k / 段数自动）：

```
yuv transcode 1044x720 -> 848x576 @855k
yuv transcode done size=16095332
part 01 ... size=7894561
part 02 ... size=8117414
```

两段 7.9MB + 8.1MB，都在 9MB 以内 ✓

## v3.8 / v3.9 自动挂载重构：不再依赖无障碍

排查「自动挂载没反应」时发现两个硬伤：

### 1. 无障碍服务在这台手机上根本没绑定

```
$ adb shell dumpsys accessibility
Bound services:{}      ← 空的
```

用 `settings put` 强设也没用，MIUI 会把它按回去。而整个悬浮球/面板都写在无障碍服务里，
**无障碍一掉，功能就等于不存在**。

### 2. 队列卡死（这就是「选了3个只下一个」和「下载完啥都没有」）

- **排队数看不到**：从选集页提交后主界面在 `onPause` 里把 `Jobs.setListener(null)`，
  队列/进度回调全丢，回到前台也不补，所以界面上看不出还有几个在排队（其实都在跑）
- **线程死了不会重启**：`enqueue` 只用 `worker == null` 判断，
  工作线程异常退出后引用还在，后续入队永远不启动新线程 → 任务无限排队、什么都不发生

### 改法

| 问题 | 改法 |
|---|---|
| 悬浮球依赖无障碍 | 拆出 `ClipService`（普通**前台服务**）承载悬浮球、面板、读剪贴板；无障碍只保留「复制按钮被点」的探测（可选加分项） |
| 进程重启后悬浮球消失 | `onResume` 里 `attach` 开着就 `ClipService.wake()` |
| 探针读剪贴板偶发 null | 拿到焦点后重试最多 5 次（每次 220ms），不再一次定生死 |
| 排队数不显示 | `onResume` 补一次 `onQueueChanged(Jobs.pending())`；文案改成「还有 N 个排队」 |
| 线程死掉任务丢弃 | `worker == null \|\| !worker.isAlive()` 才复用；`finally` 里若队列非空就补开线程 |

实测：选集页勾 3 个 → 状态行显示「处理中 51% · 还有 2 个排队」，P5/P6/P7 依次完成。

## v3.5 转码失败的真凶（高通 Codec2 的 surface 缺陷）

为了让 30 秒 8MB 这种视频变小，加了「最高码率」设置（默认 900k）。
但实测**转码在这台手机上跑不起来**，试了六种修法全部失败：

| 尝试 | 结果 |
|---|---|
| 宽高对齐 8 / 16 的倍数 | 仍失败 |
| CBR 改 VBR | 仍失败 |
| 低码率时限制分辨率 | 仍失败 |
| 去掉 rotation、改用 muxer orientation hint | 仍失败 |
| 换软件编码器 `c2.android.avc.encoder` / `OMX.google.h264.encoder` | 仍失败 |
| 先喂一帧再取编码器输出 | 仍失败 |

底层日志指出了真正原因：

```
Codec2Client: setOutputSurface -- failed to set consumer usage (6/BAD_INDEX)
CCodecBufferChannel: [c2.qti.avc.encoder] work failed to complete: 14
```

**解码器无法把画面交给编码器的输入表面** —— 这是高通 Codec2 在该机型上的缺陷，
不是参数没调对，所以换编码器、换码率、换对齐都绕不过去。

### 解法：YUV 直通转码（`TranscoderYuv`）

既然「解码器 → 编码器表面」这一步是坏的，就**完全不用 Surface**：
解码器输出 `COLOR_FormatYUV420Flexible` 的 ByteBuffer，逐平面拷进编码器的输入 Image
（顺带做最近邻缩放），编码器也配成 `YUV420Flexible`。

**实测通过**：1044x720 @855k 的抖音视频转码成功（49 秒转完 130 秒素材），
30MB → 20.9MB，切成 7.1 / 6.6 / 7.0 三段。

注意点：
- 必须锁 `BITRATE_MODE_CBR`，否则默认 VBR 会超到 1.5 倍以上（实测 855k 跑成 1.28M）
- 转码速度约 2.5 倍速，130 秒素材要 50 秒左右
- 解码出的帧是「未旋转」的，旋转角改由 `MediaMuxer.setOrientationHint()` 写进文件

### 实测数据（v3.6）

| 源 | 码率 | 输出 | 结果 |
|---|---|---|---|
| 14.96MB / 53s | 2.24Mbps | 6.46MB · 848x368 | 单片，实测 967k（855k 视频 + 音频）|
| ~30MB / 130s | ~1.9Mbps | 20.9MB | 3 段 7.1/6.6/7.0 |
| 922x720 / 55s | — | 848x656 · 855k | 3 段 6.7/6.7/6.6 |

按 855k 估算：**30 秒视频约 3.2MB**（原来是 8MB）。

### 现在能立刻减体积的办法

- **B站**：设置里把「高清 480P」关掉，走 360P（约 600kbps），体积直接减半
- **抖音**：分享接口只提供一档码率（`bit_rate` 数组实测不存在），只能靠转码压

## v3.4 切分畸形 + 老链接重复识别

### 切出「28MB + 2MB」的原因

按体积切分的逻辑是：先按字节总量算出段数，再用「累计字节」反推切点所在的秒数。
问题是**码率不是均匀的**——快镜头多的一分钟能占一大半体积，于是切点被推到很后面，
切出 28MB + 2MB 这种畸形片段。

改成：**先按时间均分算切点，再吸附到最近的关键帧**，体积自然就均衡了。
实测同一条 30MB 抖音视频：改之前 28+2，改之后 7.2 / 9.0 / 6.9 / 6.6 MB，四段都在 9.6MB 以内。

### 一进应用就把最后那条链接又跑一遍

原来只比较「链接 + 剪贴板时间戳」的内存变量，**进程被杀重启后变量就丢了**。
现在：

- 签名持久化到本地，重启后照样记得
- 只要这条链接**已经成功处理过**，就只记下不处理 —— 想重下请手动点「粘贴」或去记录里重试
- 真正新复制的链接照常自动识别

### 抖音为什么总是「原画」

抖音分享页只给**一个**播放地址（`play_addr`），没有低清档可选（B站有 DASH 多档，抖音没有）。
所以画质没法选，只能靠压缩：**当原始码率超过每段上限对应的码率时**会自动转码压缩，
不超过就直接用原画（避免白压一次损失画质）。

如果你希望抖音视频一律压缩到更小，告诉我，我把判定阈值调严就行。

## v2.6 抖音「能下不能切」的真凶：负数时间戳

v2.5 之后抖音链接能解析、能下载，但很多卡在最后一步：**「读取样本大小失败」**。

拿真实链接追踪下来，文件本身是**完全正常的 MP4**（`ftyp isom`，avc + aac 双轨），
问题出在这一句：抖音视频的**首帧时间戳是负数**（实测 `t = -46439`，约 -46ms）。

老代码里到处是 `if (t < 0) break;` —— 把「负时间戳」当成了「没有样本了」，于是：
- `cumBySecond()` 一个样本都没读到 → 报「读取样本大小失败」
- `extractRange()` 一开始就 break → 切出来的片段是空的
- 我新加的 `validMedia()` 也踩了同一个坑 → 把好视频判成坏文件

### 修法

| 位置 | 改法 |
|---|---|
| 判断「还有没有样本」 | 改用 `getSampleTrackIndex() < 0`，不再用时间戳正负 |
| 时间戳分桶 | `Math.max(0, t / 1e6)`，负数归到第 0 秒 |
| 切分输出 | 首帧若为负，整体平移（`shift = -firstT`），保证输出从 0 开始 |
| 转码 | 同样平移，避免给编码器喂负 PTS |
| 有效性校验 | 改成「真读一个样本出来」，比看时间戳靠谱 |

实测同一条抖音链接（`v.douyin.com/y9EJsLDjHYD` 那条蛋仔派对）：修复前必失败，
修复后正常切成 2 段（5.5MB + 4.2MB）。

- 一条视频的多个 CDN 地址**逐个试**，某个域名解析不了（`aweme.snssdk.com` 偶发）
  或返回错误页会自动换下一个
- 下载后**校验是不是真视频**，不是就换地址，不会把错误页当视频去切
- 失败也会写进处理记录（红色 + 原因 + 「重试」按钮），失败记录不参与「已处理」判定

## v2.1 修复：短链去重失效 + 多分P 视频

### 短链为什么不提示「已经处理过」

之前的查重是在**入队前**用正则从 URL 里扣 `BV号`。但 `b23.tv/xxxx` 这种短链里根本没有 BV 号，
所以扣出来是空 → 判定为「新视频」→ 直接开跑。**这是用户反馈「重复粘贴直接处理了」的根因。**

现在改成**两道查重**：

1. 入队前：URL 里能扣到 BV 号的，先快速拦一次（省一次网络请求）
2. **解析之后**：短链跟随后拿到真实 bvid，再查一次 —— 短链也能拦住

解析后才拦的代价是每次重复粘贴会先解析（约 1 秒），换来的是短链不再漏。

### 多分P 视频

一个链接里带多个分P（如《数据结构》173 P）时，解析后弹窗让你选：

- **全部下载**：自动跳过已经在记录里的分P
- **只下第 1 P**
- **取消**

去重 key 从 `bvid` 改成 `bvid_pN`，所以 173 个分P 是 173 条独立记录，不会互相判重。
链接里如果本来就带 `?p=5`，就直接下第 5 P，不再问。

实测：`BV1nJ411V7bd`（173 P）正确弹出「这个视频有 173 个分P」；

## v1.5 新增：短片高码率自动强压

**规则**：每段至少 2 分钟。如果「2 分钟的内容」本身就超过单段上限（默认 10MB），
说明源码率太高 —— 这时候继续切只会切出一堆几十秒的碎块，所以**先压再切**。

- 触发条件：源平均码率 > `单段上限 × 8 / 120s`（默认 9.6MB → 约 640kbps）
- 压缩目标：`(上限 × 8 / 120) × 0.92 - 64k` ≈ 525kbps（留 8% 余量给容器开销）
- 典型效果：2 分钟 15MB（约 1000kbps）→ 压到 525k → 约 8.6MB，**一个文件搞定**，
  而不是切成 6 个 20 秒的碎片
- 不触发时（码率正常）：仍然走无损直切，一秒不重编码

## 用

三种入口：

1. **分享**（推荐）：B站视频页 → 分享 → 选「B站切片」，自动开始
2. **粘贴**：复制链接 → 打开 App → 从剪贴板粘贴 → 开始
3. **手动**：直接把链接打进输入框

两个参数：

| 字段 | 说明 |
|---|---|
| 每段上限 | 默认 9.6MB，保证手机上传限制 10MB 不炸 |
| 段数 | **留空=自动**：够切就行，不重新编码，零画质损失 |

「段数」填了数字才会真压缩。比如填 1，就把整片压到 1 个 9.2MB 以内的文件；
填 2 而原片需要 5 段，就按 2 段的总预算重新编码。

成品在：`手机存储/Download/B站切片/<视频标题>/`

## 怎么实现的（为省体积做的取舍）

| 环节 | 做法 | 为什么这么做 |
|---|---|---|
| 取流 | `x/player/playurl?qn=16&platform=html5` | 免登录直接返回**单个 mp4**，不需要 DASH 音视频合流，省掉整个 ffmpeg |
| 下载 | HttpURLConnection + Referer | B站 CDN 校验 Referer，缺了会 403 |
| 压缩 | MediaCodec 硬编 H.264（Surface 直通） | 手机自带硬件编码器，速度约 25 倍实时（213 秒片子 8 秒压完） |
| 音频 | MediaExtractor → MediaMuxer 原样搬 | 不重压，省时间也不掉音质 |
| 切分 | MediaExtractor → MediaMuxer 重封装 | 只搬数据不重编码，切点吸附到关键帧 |
| 切点 | 按**字节数**均衡，不按时长 | 码率不均时按时长切会出现 11MB/7MB 这种大小差 |
| 输出 | MediaStore.Downloads | 不需要任何存储权限 |
| 片库 | 直接查 MediaStore（RELATIVE_PATH LIKE） | 卸载重装后依然能看到自己下过的片子 |
| 分享 | 自写 VideoProvider（不用 AndroidX 的 FileProvider） | 微信读不了 MediaStore 的 URI，必须走自己的 Provider 授权 |
| 压缩决策 | 判断「2 分钟能否装进一段」再决定压不压 | 短片高码率硬切会变成一堆几十秒的碎片，体验差且没必要 |
| 封面 | MediaMetadataRetriever 按 12%/35%/60% 取帧 + 黑场检测 | 首帧常是淡入黑屏，直接取首帧会得到一片黑 |
| 封面缓存 | LruCache + 磁盘 jpg（key 带版本前缀） | 重进片库秒出；算法改了换前缀即失效 |
| 回调 | 同一 key 的请求排队，完成后统一回调 | 页面重绘后新视图会错过回调，封面就一直空白 |
| 保活 | 前台服务 `dataSync` | 处理时人切去微信，进程不会被回收 |
| UI | 纯代码布局，无 XML 无 AndroidX | 整个 APK 29KB |

## 踩过的坑（都已修，改代码前先看）

1. **`releaseOutputBuffer(render=true)` 会阻塞**：编码器输入队列满时，渲染会卡住；而编码器又等着出队。
   正确顺序是**先把编码器输出清空，再渲染**，否则真机上必卡死（模拟器反而看不出来）。
2. **`MediaExtractor` 忘了 `selectTrack`**：`getSampleTime()` 直接返回 -1，切出来是 0 字节的空文件。
3. **`dequeueOutputBuffer` 超时给太大**：给 10 秒的话，每次空转白等 10 秒，213 秒的片子要跑十几分钟。
4. **不要盲目按预算顶码率**：预算算出来比源码率还高时，重新编码只会让文件更大、画质更差。
   现在的规则是：不需要压缩就不压缩（无损切），要压缩时目标码率一定低于源码率。
5. **微信收不到 MediaStore 的 URI**：直接 ACTION_SEND 一个 MediaStore 视频给微信，微信会打开又秒退。
   必须复制到自己的缓存目录，用自建 ContentProvider 授权（`grantUriPermissions`）再发。
6. **构建脚本要判 javac 退出码**：中文系统下 javac 报的是「错误:」，grep `error:` 会漏，
   导致编译失败却继续打包，最后运行时 `NoClassDefFoundError`。
7. **`Log` 名字会被自己的接口遮住**：Pipeline 里定义了 `interface Log`，再调 `android.util.Log.w`
   就编译不过，必须写全限定名。
8. **封面回调丢视图**：`cover()` 里有「已在加载中就直接 return」的守卫，页面重绘一次后
   新视图就永远拿不到图（表现为一直灰块）。改成按 key 排队、加载完统一回调。
9. **`ThumbnailUtils.createVideoThumbnail(ContentResolver, ...)` 在 SDK 里不存在**，
   只有 `(File,...)` 和 `(String,int)` 两种；拿 MediaStore 条目取帧要用
   `MediaMetadataRetriever.setDataSource(Context, Uri)`。
10. **剪贴板在 Android 10+ 只有前台能读**：所以是「App 在前台时每秒轮询 + 回到前台时检查」，
   做不到完全后台静默监听（系统限制，不是实现问题）。

## v6.5 有些视频读不到时长：三级兜底

### 现象

处理某些视频时报「读不到视频时长，无法切分」，片库里这些片段也不显示时长。

### 根因

系统 API 对**碎片化 MP4（fMP4）**这类容器给不出时长。实测：

```
t_frag.mp4（ffmpeg -movflags frag_keyframe+empty_moov）  → MediaStore duration=0
t_hevc.mp4（普通 MP4，HEVC）                             → MediaStore duration=6000
```

而旧代码里读时长有两套，标准不一：

- `Pipeline.durationOf`：MediaExtractor → MediaMetadataRetriever（两级）
- `Splitter.durationUsOf`：**只有 MediaMetadataRetriever**（一级）

MediaMetadataRetriever 恰恰是对 fMP4、缺 moov 时长、带 elst 编辑列表的文件最不擅长的那个。
所以切分阶段最容易炸 —— 报的就是那句「读不到视频时长」。

这类文件通常来自：抖音/快手导出的流式 MP4、HLS 转存、部分剪辑软件或录屏工具；
还有一种是自己产物 —— 如果源本身够小、不需要压缩，我们是**原样复制**，
容器里没有时长，它就一路继承下去。

### 改法：三级兜底

```java
1) MediaExtractor 读轨道头 KEY_DURATION   // 几毫秒，最稳
2) MediaMetadataRetriever                 // 老办法
3) 逐样本推进到结尾取最后时间戳             // 不解码，只读包头，几千样本几十毫秒
```

- `Splitter.durationUsOf` 与 `Pipeline` 统一走这一套
- 片库侧也补了兜底：MediaStore 给的 `durMs` 为 0 时，本地读一次再显示
  （只对异常文件触发，不影响正常列表速度）
- 三级都失败时的报错会带上文件名与大小，便于定位是哪个文件

### 实测

| | 修复前 | 修复后 |
|---|---|---|
| 处理 t_frag.mp4（fMP4） | 读不到时长 → 失败 | 处理成功 |
| 片库显示该片段 | 无时长 | `1 段 · 0.52 MB · 0:06` |

## v6.6 顺着「读不到时长」往下查，又挖出四处

时长那个问题本质是「系统 API 在某些输入上会失效」。按这个思路把几处依赖
系统能力的地方过了一遍，四个都有真实的失效场景：

### 1. 音轨格式不被 MP4 接受时，整单失败

`mux.addTrack(音频 format)` 遇到 opus / flac / ac3 会抛异常，以前直接让整个转码失败。
现在退化成**无声视频**（至少能用），并在界面日志里说明「源音轨 MP4 装不下，这一版成品没有声音」。

实测：opus 音频的 mp4 → `audio track rejected, mute output` → 转码 781ms 成功，产出无声可用视频。

### 2. 源是 HEVC/AV1、转码又失败时，会产出微信播不了的段

转码失败原来一律「改为直接切原片」，但原片是 HEVC 的话，切出来的段微信和相册很可能打不开。
现在先看源编码，不是 `video/avc` 就明确报错，不产出坏文件。

实测：HEVC 源正常转码 → 输出 `h264 + aac` ✓

### 3. 删除片段后留下空文件夹（积累到 122 个）

删文件不删目录，`Download/B站切片/` 越用越脏。实测这台机器上 175 个目录里有 **122 个是空的**。

- 单个删除、重新处理清旧片段之后，目录空了就顺手删掉
- 设置里加「清理空文件夹」一次性收尾（只删空目录，有内容的一个不动）

实测：175 → 53 个目录，空目录 0。

### 4. 分享前复制文件还在用 64KB 小循环

`withShareUri` 要把片段复制到 cache 才能交给微信，原来是一趟 64KB 地搬。
改成通道传输（`FileChannel.transferTo`），9MB 的文件从约 1 秒降到约 0.1 秒。
「发整组」时是 N 个文件叠加，收益更明显。

## v6.7 缩略图与片库信息的两处打磨

继续按「异常输入会不会让某个环节退化」的思路测，这次落在缩略图上。

### 1. 暗场景视频的缩略图全黑

四个候选时间点（12% / 35% / 60% / 0）都是暗帧时（夜景、室内暗光），缩略图看起来就像加载失败。
实测片库里一条星空场景的片段，缩略图整块黑，只有一个亮点。

改了两件事：

- `isDark` 阈值从平均亮度 24 放宽到 45，覆盖「整体偏暗但不算全黑」的情况
- 命中暗帧时做一次提亮：亮度 ×1.9、黑位抬 12（`ColorMatrix`），缩略图尺寸下噪点看不出来

另外补了个小坑：**1 秒左右的短视频只取第 0 帧**，而很多片子开头是黑场淡入。
现在短视频也取中间帧（`durMs × 0.5`）再退回 0。

缓存版本号升到 `v5_`，旧的黑缩略图会重新生成。

实测：那条星空片段从「纯黑」变成能看清画面和字幕。

### 2. 单段行补上时长

原来单段行只显示文件大小（`6.45 MB`），要判断这段多久得看组信息或点开。
现在两处渲染都带上时长：`6.45 MB · 0:53`。

## v6.8 两个真问题：1 秒碎片段 / 复制链接不响应

### 1. 第二段只有 1 秒，后面全没了

现象：54 秒的视频切成两段，第一段 53 秒，第二段 1 秒。

根因在切点吸附。切法是「按时间均分 → 把切点挪到最近的关键帧」，但没有距离上限。
关键帧稀疏的片子（长 GOP、录屏、第三方转码）可能只有开头和结尾两个关键帧：

```
54 秒视频，关键帧只有 0s 和 53.5s，计划切 2 段 → 目标切点 27s
最近的关键帧是 53.5s → 切点被挪到 53.5s → 第二段只剩 0.5 秒
```

现在：

- 只在目标点附近（段长的 25%，最少 1 秒）找关键帧
- 附近没有就**放弃这个切点**（宁可少切一段，也不从非关键帧开始 —— 那样开头会花屏直到下一个关键帧）
- 尾段或中间段短于「段长的 1/3 且不超过 3 秒」时，直接合并
- 段数被调整时在界面日志里说明：「关键帧不够密：本来切 3 段，改成 1 段」

实测（54 秒、仅两个关键帧、计划 3 段）：
`切点调整：3 段 -> 1 段（关键帧不够密，避免切出极短段）` → 输出一个完整 54 秒文件。

### 2. 复制链接没反应（真正的原因）

这条查得比较久。表面看是「处理中复制的链接不排队」，但日志显示：

```
clip sig=...BV1xx...#1795601647351  last=...BV1xx...#1795601647351  same=true
```

去重用的是「链接 + 剪贴板时间戳」。而**小米等 ROM 上重新复制同一段文字，
剪贴板时间戳不会变** —— 于是同一条链接复制第二遍，永远被判成「同一条内容，跳过」。

两处修改：

- 去重条件从「内容相同」改成「**内容相同且发生在 30 秒内**」，过了窗口就当作新的一次复制
- 去掉了「这条以前下过就静默跳过」的判断 —— 去重本来就该由剪贴板时间负责，
  按历史记录跳过会让「复制了但什么都不发生」更隐蔽。想重切同一视频现在也会走一遍（重复时仍会弹确认）

实测：同一条链接超过 30 秒后再触发，会重新解析（假链接返回「视频不存在」即证明已进入流程）。

## v6.9 复制链接没反应：根因是无障碍被系统关了（不是代码）

上一版把去重逻辑改成「30 秒窗口」，以为修好了。这版继续查，发现两件事：

### 1. 后台轮询这条路其实是死的

```
poll: no clip (cm=true)
```

Android 10+ 起，非前台应用读剪贴板一律返回空 —— 无障碍服务也拿不到（至少这台 MIUI 上不行）。
所以「后台定时读剪贴板」这条路根本走不通，后台复制只能依赖**无障碍监听到「复制」被点击**，
再通过探针 Activity 抢焦点去读。

### 2. 而这台机器上，无障碍服务压根没开

```
$ adb shell settings get secure enabled_accessibility_services
(空)
$ adb shell settings get secure accessibility_enabled
0
```

`accessibility_enabled = 0`，服务列表是空的。也就是说「复制」点击根本没人监听，
复制之后当然什么都不发生 —— 代码再怎么改都不会有反应。

原因很可能是反复重装 APK：MIUI 在应用更新后会自动撤销无障碍授权（已知行为）。

### 改法：把它变成看得见的状态

设置页顶部新增一行状态，点一下直接跳到系统无障碍设置：

| 状态 | 含义 |
|---|---|
| ✓ 复制监听已连接 | 正常，复制链接会自动处理 |
| ⚠ 复制监听未运行 | 系统里还勾着，但服务没起来（被杀），点一下重开 |
| ✕ 复制监听未开启 | 系统里就没勾选，点一下去开 |

实现上给 `ClipWatchService` 加了 `connected` 静态标记 + `enabledInSettings()`
（读 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES`）。

### 顺带把后台去重也统一了

`ClipService.onUrlFound` / `poll` 里还有一套独立的 `sig == lastSig` 判断，
同样会因为「小米重新复制同一段文字时剪贴板时间戳不变」而永久跳过。
现在统一成 `isDuplicate()`（30 秒窗口）+ `rememberSig()`。

### 切分修复的验证（这次做了对照）

| 场景 | 结果 |
|---|---|
| 正常关键帧（60 秒，每 1 秒一个）计划 3 段 | `n=3 cuts=[20s, 40s]` → 三段各 500 帧（20 秒）✓ |
| 稀疏关键帧（54 秒，只有 0s 和 53.5s）计划 3 段 | `切点调整：3 段 -> 1 段` → 输出完整 54 秒文件 ✓ |

### 再确认一次后台轮询是死路

```
I BiliSlicer: poll: no clip (cm=true)
```

`hasPrimaryClip()` 在后台一律 false（Android 10+ 限制，无障碍服务也不例外）。
所以别再指望「后台定时读剪贴板」兜底，后台复制只能靠无障碍点击。

### 补一个队列去重

`Jobs.enqueue` 现在会检查队列里有没有同一条链接（还没开始跑的），
避免复制事件重复触发或用户连点导致同一条视频排两遍。

### 关键结论

代码链路没问题；「复制了没反应」的原因是**无障碍授权被系统撤销**。
MIUI 在应用更新后会自动撤销无障碍授权 —— 也就是说每装一次新包，
都要回去把「片匠」的无障碍开关重新打开一次。

设置页顶部那行状态就是为此加的：正常显示「✓ 复制监听已连接」，
被撤销时显示「✕ 复制监听未开启（点这里去开启）」，点一下直达系统设置。

## v6.11 「用着用着又失效」的真凶：force-stop 会关掉无障碍

这版把无障碍真正开起来跑了完整链路，同时挖出两个真问题。

### 1. 强行停止应用 = 系统关掉它的无障碍服务

测试时的固定动作：

```
adb shell am force-stop com.zhuanz.bilislicer   # 冷启动，干净
adb shell am start -n .../.MainActivity
```

结果每次打开完无障碍，下一次冷启动就又变回：

```
enabled_accessibility_services = null
accessibility_enabled = 0
```

原因是系统认为「用户强制停止了应用」，于是把它的无障碍服务一起停掉。
**用户在最近任务里划掉应用，效果完全一样** —— 这就是「用一阵子又不好使」的由来。

对照实验：用 `am start` 直接启动（不 force-stop）时，安装之后无障碍也保得住，
服务状态 `settings get secure enabled_accessibility_services` 一直是本包。

### 2. 服务明明连着，界面却显示「未开启」

修完第一个问题后发现：`dumpsys` 里 `label=片匠` 说明服务在跑，
但设置页那行还是「✕ 复制监听未开启」。

原因：

```java
Settings.Secure.getString(cr, Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES)
// Android 10+ 普通应用读这个键被拦，永远拿到 null
```

改成走 `AccessibilityManager.getEnabledAccessibilityServiceList()`（不需要权限、返回真实状态），
并让界面以 `ClipWatchService.connected` 为准（服务真的连着），勾选状态只用来区分
「勾了但没跑」和「压根没勾」。

### 3. 把提示挪到主界面

原来只有设置页里那一行，藏得太深。现在主界面 chips 下面有一条：

```
⚠ 复制监听已关闭（复制链接不会自动处理）· 点这里开启
```

点击直达系统无障碍设置；服务连上后回来提示条自动消失（实测）。
